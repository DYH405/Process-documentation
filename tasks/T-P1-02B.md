## 执行流程（强制，顺序不可反）

1. 先回【计划】：列出要新增/改动的文件、每个改动点（函数/脚本步骤级）、
   汇总表字段设计、分批执行方案、熔断条件、风险、预计影响行数。
2. 涉及代码/脚本改动，先贴拟改关键片段（每处 ≤30 行），只展示不落盘。
3. 等用户明确回复“放行”后，才允许写入文件、构建、运行。
4. 计划未放行前只允许只读查看，禁止修改源码/配置/地图/参数/文档。
5. 实现中发现计划外问题，先停下报告，不要顺手修。

## 终端命令执行规则（强制）

- 环境限制：agent 在 VS Code 插件中调用终端拿不到输出，结果为空。
- 因此：任何需要终端执行的动作（git、grep、ls、cat、colcon build、ros2、
  脚本运行等），agent 一律不自行调用终端，改为输出“待执行命令清单”。
- 命令清单格式：编号 | 目的 | 命令全文 | 预期输出特征（几行/含什么关键字）。
- 分批执行：按步骤分组，每组 ≤5 条，用户贴回结果后 agent 再判断下一步。
- 输出收窄：可能 >50 行的命令，必须自带 grep/head/tail/--stat 收窄，
  不许让用户贴几千行。
- 禁止假设成功：用户未贴结果前，agent 不得写“已通过/已验证/构建成功”。
  需要结果才能继续的，明确写“等待命令 N 输出后继续”。
- 文件读取/搜索工具（Read/Edit/Grep）可正常使用，不受此限。

## 必须做

### 1. 只读盘点（计划阶段先做，回传汇报）

a. 当前 run CSV 实际表头全文（逐列列出，不臆造）。
b. run_one_experiment.sh 的入参、退出码含义、日志目录结构。
c. experiment_logs/ 下已有 run 目录清单（run_id、是否含 pose_trace、是否有 truth_last_pose）。
d. 现有 4 个 run（12.11 里的 run1~run4）分别对应哪些 run_id，补齐对照。

### 2. 批量循环脚本（建议 scripts/run_batch_experiments.sh，命名可议）

a. 外部循环调用 run_one_experiment.sh，不修改 run_one_experiment.sh 内部。
b. 参数：目标 valid 轮数（默认 10）、最大总轮数（默认 15）、单轮超时（默认 15 min）。
c. 每轮结束后立即做轻量 valid 判定（见第 3 条），invalid 也保留原始数据，不删除。
d. 支持分批执行：脚本可指定“本次跑 M 轮”，便于用户分段贴结果。
e. 每轮打印一行摘要（run_id、exit code、valid/invalid、耗时），不刷屏。

### 3. invalid 判定规则（强制，替代旧版）

满足任一即 invalid：

a. 任一 pose_trace 采样点 |gt-amcl| > 1m 且持续 > 10s
b. 末点 |gt-amcl| > 0.5m
c. 日志出现 "Starting point in lethal space"
d. run_one_experiment.sh 退出码非 0

记录：invalid 原因分类 + 跳变落点坐标 + 跳变发生时刻 + 跳变前最近巡逻点。

注意：valid 判定与 run 是否“导航成功”解耦；8/10 成功但定位可信的轮仍可 valid。

### 4. 汇总脚本（建议 scripts/summarize_baseline.py，命名可议）

a. 输出独立汇总 CSV：experiment_logs/baseline_summary.csv，不改 run CSV。
b. 字段（至少含）：

```
run_id, run_exec_ok, valid, invalid_reason, total_goals, succeeded, failed,
timeout, canceled, rejected, total_time_s, gt_last_x, gt_last_y, gt_last_yaw,
amcl_last_x, amcl_last_y, amcl_last_yaw, pos_err_m, yaw_err_deg,
max_dev_m, max_dev_dur_s, lethal_space_hit, trace_path, note
```

c. 统计报告（stdout 或 md 文件）：仅对 valid 轮计算
   成功率、耗时、pos_err、yaw_err 的 n / mean / median / std / min / max。
d. 额外输出 invalid 轮统计：轮数、原因分布、跳变落点是否聚集在某个巡逻点附近。

### 5. 采集执行（分批，用户跑命令）

a. 第一批先跑 3 轮，贴回摘要，确认脚本与判定正常。
b. 确认后继续分批，直到 valid 达 10 或触发熔断。

### 6. 熔断条件（防跑偏，强制）

a. 总轮数达 15 但 valid < 10 → 停止，报告“有效轮不足”，分析 invalid 分布。
b. 连续 3 轮 invalid → 停止，报告“系统性问题”，不继续堆轮次。
c. 单轮超过 15 min 未结束 → 强制终止该轮，记 invalid，报告。
d. 出现计划外文件改动或参数改动迹象 → 立即停止报告。

### 7. 文档同步（强制）

a. 交接文档头部时间改实际日期，阶段保持“P1 收口（可复现基线）”。
b. 新增或续写基线结果章节：valid 轮统计、invalid 分布、yaw 偏差复核。
c. 12.11 对照表每行补 run_id。
d. BUGLOG 补“跳变落点接近 wp3”观察（02A-FIX 遗留项）。
e. 回传必须列：更新了哪个文件、哪一节、新增/修改了什么。

### 8. 代码规范（强制）

a. 新增脚本逐行中文注释：函数头、关键逻辑、每个参数都要说明用途与默认值。
b. 不允许无注释的复杂逻辑块。

### 9. 禁止重构（强制）

a. 不得重命名现有参数、变量、函数、文件、话题名。
b. 不得合并、拆分、搬迁现有函数。
